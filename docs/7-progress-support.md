## スコア付与タイミングと日誌の保存・確定（現状整理）`260211-水`

### ゴルド・EXPの付与タイミング（今の仕様）

- **習慣**
  - 付与タイミング: 習慣のチェック（または数値変更）を送信した**その瞬間**

  - 実装: `POST /api/habit-logs`。habit_logs 更新と同時に、差分で profiles の points / exp_body・exp_mind・exp_spirit を加減算。良習慣はチェックで加算・外しで減算。悪習慣はチェックで減算・外しで加算（週末除外時は悪習慣は加減算なし）。

- **ToDo**
  - 付与タイミング: タスクを**完了にした瞬間**
  - 実装: カンバン・ToDoサマリーの `handleTaskCompletion`。todo_logs に記録し、`is_special` かつ報酬設定があるタスクのみ profiles に加算。**未完了に戻す**と `handleTaskUncompletion` で todo_logs 削除＋profiles から減算。
- **日誌（AI）**
  - 付与タイミング: **一括生成（AI判定を実行／再生成）**を実行したときのみ
  - 実装: `POST /api/ai/batch`。体調・気分スコアからポイント/EXPを計算し、daily_logs の ai_* カラムを更新し、**同時に profiles に加算**。個別の「判定API」(`/api/ai/judgment`) はスコアを返すだけで DB は更新しない。UI の「AI判定を実行」は batch を呼ぶため、実質「一括生成のときだけ」profiles に反映。

- 習慣・ToDoは「アクションした瞬間」に profiles に反映。
- 日誌のゴルド/EXPは「AI一括生成を実行したとき」のみ profiles に反映。

### 日誌の「保存」と「確定」（今の仕様）

- **保存**
  - **日誌本文・一言感想**: `JournalImpressionSections` で入力から **500ms デバウンスの自動保存**。`daily_logs.journal_text` / `one_line_comment` を直接 update。

  - **権利（利用ポイント）**: 「日誌を保存」ボタンで `handleSave` → `daily_logs` の権利カラム（right_*_count）のみ更新。本文・一言はここでは触らない（上記で自動保存済み想定）。

  - サーバー側: `PUT /api/daily-logs` で日誌ID・本文・一言・権利をまとめてバリデーション・更新するAPIあり（クライアントは上記の経路で保存）。

- **確定**
  - `daily_logs.is_confirmed`（boolean）。

  「確定」ボタンで true、「確定を取り消す」で false。

  - **確定済みの過去日誌**は編集不可。
  **当日の日誌**は確定しても編集可能。確定取り消しは**全日誌**で可能。
  - 確定済みの日誌では「AI判定を実行」は不可（再生成も不可）。

「保存」と「確定」の考え方をどうするか（例: 確定した日だけ profiles に反映する、確定前は下書き扱いにする など）は、ここまでの現状を前提に仕様として決めていく想定。

###### **【メモ】** 表示名がデフォルトになる原因調査

あらすじ・アドバイスに設定した名前ではなくデフォルト名（辰彦・勇者など）が出る場合の切り分け用。詳細は `docs/appendix/表示名がデフォルトになる原因調査.md` にも記載。

- **流れ:** 設定画面で表示名・チェック保存 → `profiles.username` / `profiles.use_username_as_display_name`。バッチAPIはここを読んで `nickname` をプロンプトに渡す。空ならデフォルト名になる。

- **原因の切り分け:**
  - 「（未設定）」→ DB の `profiles.username` が空、または `use_username_as_display_name` が false の可能性。設定画面で保存・チェックを確認。

### Google OAuth「Error 400: redirect_uri_mismatch」の対処（Supabase 用）

**原因:** ログイン後に戻る URL（リダイレクト URI）が、Google 側の「承認済みのリダイレクト URI」に登録されていない。

**やること: Google に「承認済みリダイレクト URI」を追加する**

1. **Google Cloud Console を開く**  
   https://console.cloud.google.com/

2. **プロジェクトを選ぶ**  
   画面上部で使っているプロジェクト（例: GOL-WEB）を選択。

3. **認証情報を開く**  
   - 左メニュー **≡** → **「APIとサービス」** → **「認証情報」**  
   - または検索で「認証情報」を開く。

4. **OAuth 2.0 クライアント ID を開く**  
   一覧の **「OAuth 2.0 クライアント ID」**（ウェブクライアントなど）の **名前** をクリック。

5. **「承認済みのリダイレクト URI」に 1 件追加**  
   - **「承認済みのリダイレクト URI」** の **「+ URI を追加」** をクリック。  
   - 次の URL を **1文字も違えず** 入力する（GOL の場合は **先頭が小文字の L**）：
     ```
     https://lridxyccbxqglnoejntz.supabase.co/auth/v1/callback
     ```
   - Supabase のプロジェクト参照が `lridxyccbxqglnoejntz` 以外の場合は、  
     **https://〈あなたのプロジェクト参照〉.supabase.co/auth/v1/callback** に置き換える。  
     （Supabase ダッシュボード → プロジェクト設定 → API で「プロジェクト URL」を確認できる。）

   画面下部の **「保存」** をクリック。

**ポイント**

- **完全一致** である必要がある（`http`/`https`、末尾の `/` の有無、ドメインも含めて一致）。
- 変更後、反映まで **数分** かかることがあるので、しばらくしてから再度ログインを試す。


### Google OAuth コールバック後にログイン画面に戻る / 「PKCE code verifier not found」の対処（Supabase + Next.js）

**症状:** Google でアカウント選択まで行くが、その後ログイン画面に戻ってしまう。または `PKCE code verifier not found in storage` というエラーになる。

**原因:** PKCE の code_verifier がブラウザとサーバーで同じクッキー名・設定で共有されていない。エラーメッセージの「use @supabase/ssr on both the server and client to store the code verifier in cookies」に従い、クッキーを共通化する必要がある。

**やったこと（GOL での対応）**

1. **共通のクッキー設定を用意**
   - `lib/supabase/cookie-options.ts` を追加し、`name: 'sb-auth-token'`, `path: '/'` などの共通オプションを定義。

2. **ブラウザクライアントで同じ設定を使う**
   - `lib/supabase/client.ts` の `createBrowserClient` に **`cookieOptions: supabaseCookieOptions`** を渡す。
   - ログイン開始時（`signInWithOAuth`）に code_verifier がこの名前・path のクッキーに保存される。

3. **サーバークライアントでも同じ設定を使う**
   - `lib/supabase/server.ts` の `createServerClient` に **`cookieOptions: supabaseCookieOptions`** を渡す。
   - コールバック時にリクエストに含まれる同じクッキーから code_verifier を読めるようにする。

4. **コールバックはサーバー側の Route Handler で処理**
   - `app/auth/callback/route.ts` で、サーバーが `cookies()` からリクエストのクッキーを取得し、同じ `cookieOptions` で `createServerClient` を作成して **`exchangeCodeForSession(code)`** を実行。
   - 成功したらセッション用クッキーをレスポンスに載せて `/dashboard` へリダイレクト。
   - コード交換はクライアントページではなく **Route Handler（サーバー）** で行う。

5. **リダイレクト先**
   - ログイン・サインアップの `redirectTo` は **`/auth/callback`** のまま（`/dashboard` に直接飛ばさない）。

**フロー**

1. ログイン画面で「Googleでログイン」 → ブラウザクライアントが `sb-auth-token` 系のクッキーに code_verifier を保存してから Google へリダイレクト。
2. Google 認証後 → Supabase が `https://localhost:3000/auth/callback?code=...` へリダイレクト。
3. `/auth/callback` の Route Handler がリクエストのクッキーから code_verifier を読み、`exchangeCodeForSession(code)` でセッション取得 → セッションをクッキーに載せて `/dashboard` へリダイレクト。

**Supabase の「Redirect URLs」**

- Authentication → URL Configuration の **Redirect URLs** に  
  `http://localhost:3000/auth/callback`（および本番用の URL）を追加しておく。

### マークダウン版とのデータの整合性についての相談（一旦保留）

**ステータス: 検討中**

#### 背景・目的

**なぜデータ連動させたいのか:**

- これまで日記として書き続けてきたマークダウン版を放置したくない

- 長年蓄積してきたデータを活用したい


**現状の課題:**

- **マークダウン版の課題**:

  - 書くこと自体が時間がかかる

  - **特にAIの処理が遅くて時間がかかってしまう**（主要な課題）

- **Web版への期待**:

  - AI処理の高速化

  - もっと手早く書ける方法があるのではないか


**検討事項:**

- 実際に運用してみないとわからないが、Web版とマークダウン版、どちらがいいのだろうか

- 両方のデータを連動させることで、比較検討しやすくしたい


#### 整合性に関する主な課題

**1. データ構造の違い**

- **MD版**: ファイルベース（1つのMarkdownファイルに1ヶ月分の日誌を集約）

- **Web版**: データベース（日付ごとに`daily_logs`テーブルに保存）

- **課題**: 同期時にデータ構造をどう対応付けるか


**2. 習慣データの整合性**

- **MD版**: 習慣名は自由記述（例: "GOLリストを記述｜ログインボーナス｜1日に一回のみ"）

- **Web版**: `habits.habit_name`は登録済みの習慣のみ

- **課題**: 習慣名のマッチング精度、マッチしない場合の対応


**3. 数値入力習慣の整合性**

- **MD版**: 習慣名に数値が含まれる（例: "懸垂｜10回"）

- **Web版**: `input_type = 'number'`の場合、`habit_logs.count`に数値を保存

- **課題**: 数値の抽出方法、複数選択肢がある場合の処理


**4. EXP配分の整合性**

- **MD版**: 完了済みToDoに`身体: +0 / 頭脳: +1 / 精神: +1`形式で記載

- **Web版**: `todo_logs.exp_body_earned`, `exp_mind_earned`, `exp_spirit_earned`に保存

- **課題**: EXP配分の同期タイミング、累積値の扱い


**5. ポイント・EXPの累積値の整合性**

- **MD版**: AI判定結果に累積値が記載（例: "身体: +4｜現在の累積 481"）

- **Web版**: `profiles`テーブルで累積値を管理

- **課題**: 同期時に累積値をどう扱うか（MD版の累積値は参考情報のみ？）


**6. 日付フォーマットの違い**

- **MD版**: `YYMMDD-W`形式（例: `251120-木`）

- **Web版**: `YYYY-MM-DD`形式（例: `2025-11-20`）

- **課題**: 日付フォーマット変換の精度（年の推測方法）


**7. データの欠損・不一致**

- **MD版にのみ存在するデータ**: なし（主要データは両方に存在）

- **Web版にのみ存在するデータ**: なし（主要データは両方に存在）

- **課題**: 同期時にデータが欠損した場合の対応


#### 整合性を保つための方針（検討事項）

**方針1: 完全同期（双方向）**

- MD版とWeb版のデータを完全に同期

- 競合解決が必要

- 実装が複雑


**方針2: 一方向同期（MD → Web または Web → MD）**

- 一方をマスターとして、もう一方に反映

- 競合解決が不要

- 実装が比較的簡単


**方針3: 選択的同期**

- 特定のデータのみ同期（例: 日誌本文、一言感想のみ）

- 整合性の課題が少ないデータから優先的に同期

- 段階的な実装が可能


#### 統一方針の決定 ✅ **確定（更新）**

**決定事項（260120-火）:**

- **方針: Web版のデータを新しいレポートファイルとしてMarkdown形式で出力する**

- **理由: 完全同期機能の実装はコストがかかりそうなので、一旦この方針で進める**

- **重要な方針変更:**

  - **既存のMD版はそのまま置いておく**（変更しない）

  - **別の場所に新しいレポートファイルとしてMarkdownファイルを出力する**

  - 既存のMD版のファイルを上書きするのではなく、新しい場所にレポートを生成する

  - 一方向同期のみ（Web → 新レポート）、MD → Web同期は不要

  - 実装が大幅に簡素化される


**基本方針:**

- **ベースは既存MD版のデータ構造に合わせて、レポート出力形式を作る**

**7. 習慣データ**: 習慣名が一致しない場合、どう対応するか？

**検討事項:**

- 新規登録（Web版に自動登録）。

- スキップ（同期しない）。

- 手動マッチング（ユーザーが対応）。


**🤖 AI推奨案:**

- **方針: 段階的なマッチング処理（推奨）**

- **マッチング優先順位:**

  1. **完全一致**: 習慣名が完全に一致する場合。

  2. **基本名一致**: 「｜」より前の部分（基本名）が一致する場合。

  3. **正規化後一致**: 空白・記号を除去して比較。

  4. **部分一致**: 習慣名の一部が一致する場合。


- **マッチしない場合の対応:**

  - **Web → MD同期時**: MD版に新規習慣として追加（Web版の習慣をMD版に反映）。

  - **MD → Web同期時**: スキップ（Web版に自動登録しない、ユーザーが手動で登録）。


- **理由:**

  1. **Web版を主に使う方針**: Web版の習慣定義を優先。

  2. **MD版の柔軟性**: MD版は自由記述なので、Web版にない習慣も記載可能。

  3. **手動マッチングは最後の手段**: 自動マッチングで対応できない場合のみ、ユーザーに確認。


- **将来的な検討:**

  - 習慣名のマッチング辞書を作成して、手動でマッピングを設定できる機能を追加。
