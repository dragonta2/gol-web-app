### Supabase Auth メール変更フロー（メモ）

設定画面からアカウント（メールアドレス）を変更する場合の Supabase 側の流れを整理。実装時参照用。

- **API:** クライアントで `supabase.auth.updateUser({ email: 新しいメール })` を呼ぶ

- **確認フロー（Secure Email Change 有効時）**
  - 新メールに「変更確認」用のトークン（または確認リンク）が送られる
  - 旧メールにも「確認」用のリンクが送られる（通知だけではない）
  - **両方のメールで確認リンクを開かないとメールは更新されない**（新メールだけ開いても変わらない）
  - ダッシュボード: Authentication > Email Templates で「Change email address」「Email address changed notification」をカスタム可能

- **トラブルシュート: 確認メールを開いたのにメールが変わらない**
  - **Secure Email Change が有効**になっている可能性が高い。Supabase Dashboard → **Authentication** → **Providers** → **Email** を開く
  - **Secure email change** が ON の場合 → **旧メールに届いたリンクも開く**（新メール・旧メールの両方で確認が必要）
  - 新メールだけで完了させたい場合は **Secure email change を OFF** にする（その場合、新メールの確認リンクを開くだけで変更完了）

- **実装時のポイント**
  - メールが届いただけでは変更されない。届いたメール内のリンクを開いて初めて変更が完了する旨を案内する
  - 変更依頼後、「新メールに送った確認リンクを開いてください」と案内する画面を用意する
  - 確認完了まで「未確認」状態の扱い（ログイン制限など）を設計で決める
  - `profiles` などでメールを表示している場合は、Auth の `user.email` を正とする（Auth 更新後に同期）

- **リダイレクト・端末の注意**
  - 確認リンクを開いたあと、Supabase が **URL Configuration** の Site URL / Redirect URLs に設定したURLへリダイレクトする。この設定が必要
  - 確認リンクは**リダイレクト先に、開く端末からアクセスできる必要がある**。ローカル（localhost）の場合は**同一PCで**リンクを開く必要がある。スマートフォンでは localhost に届かないため「ページを開けません」になる。本番では Site URL / Redirect URLs に本番URLを設定すればスマホからも問題なく完了できる

- **参考:** [Supabase Auth - updateUser](https://supabase.com/docs/reference/javascript/auth-updateuser)、Email Templates（Change email address）

## ドキュメント書式統一ルール --------------​

**適用範囲:** プログラミングコード以外のすべてのドキュメントファイル

- **Markdownファイル**（`.md`）: README.md、設計書、進捗表、開発ログ、メモ類など
- **テキストファイル**（`.txt`）: すべてのテキストファイル
- **その他のドキュメント形式**: すべてのドキュメントファイル

**⚠️ 除外対象:**
- プログラミングコード（`.ts`, `.tsx`, `.js`, `.jsx`, `.py`, `.sql` など）
- 設定ファイル（`.json`, `.yaml`, `.toml` など）
- その他のコードファイル

**⚠️ 重要: このルールは、コード以外のすべてのドキュメント・テキストファイルに例外なく適用される。**

#### 日付の並び順ルール

- **すべての日付を伴う記録は降順（新しい日付が上）**

- 最新の情報が常にファイルの上部に来るようにする

- 適用対象:
  - 進捗表（`03-project-progress.md`）
  - 開発ログ（`04-dev-log.md`）
  - メモ類（`7-progress-support.md`など）
  - その他、日付見出しを持つすべてのファイル

- 新しい日付の追記は、既存の日付の上に挿入

- **メモ類への追記ルール:**
  - AIがメモ類（`7-progress-support.md`など）に追記する場合は、原則降順（後入れ先追加）で記載する
  - 新しい日付のセクション（`## YYMMDD-曜日`）を一番上に作成し、その中に新しい内容を記載する
  - 既存の日付セクションは新しい日付セクションの下に配置する

#### インデントルール

- **見出し（すべてのレベル）はインデントなし**

  - 折りたたみ機能を正常に動作させるため

- リストの第1レベルはインデントなし

- ネストされたリスト（第2レベル以降）のみインデントを付与（2スペース）

#### 表記ルール（Table・リスト）

- **特別な指示がない限り、Table（表）表記は使わず、リストで書く**

- **リストの各項目の間には改行を1つ入れる**

#### 改行ルール

- **見出しの前の改行ルール**

  - `## レベル2`の見出しの前には、3つの改行（空行2つ含む）

  - `### レベル3以降`の見出しの前には、2つの改行（空行1つ含む）

- **リストや箇条書きの前の改行ルール**

  - `-` で始まるリスト行の前には、2つの改行（空行1つ含む）

  - `・` で始まる箇条書き行の前には、2つの改行（空行1つ含む）

  - `1.` `2.` `3.` などのオーダーリスト行の前には、2つの改行（空行1つ含む）

- **すべてのリストブロックの後ろにつねに改行を入れる**

  - 人間の読みやすさを重視するため

  - 第1レベルのリスト、ネストされたリスト（第2レベル以降）ともに、リスト項目の終了後に空行を2行追加（改行2回で、間に空行が入る）

  - ネストされたリストにも適用される（読みやすさのため）

- **ピリオド（.）で終わる文の後ろの改行ルール**

  - **⚠️ 必須: ピリオド（.）で終わる文の後ろには、必ず2個改行（空白行2つ）を入れる**

  - 適用対象: すべてのドキュメントファイル（Markdown、テキストなど）

  - 例: `**理由:**` の後ろ、`**決定事項:**` の後ろなど、ピリオドで終わる文の直後に空行2つを入れる

  - これにより、次のセクションやリストとの間が明確に区切られる

  - **このルールは、コード以外のすべてのドキュメント・テキストファイルに例外なく適用される**

- **リスト（オーダーリスト、箇条書き）の後ろの改行ルール**

  - **⚠️ 必須: すべてのリスト（`1.` `2.` `3.` などのオーダーリスト、`-` で始まる箇条書き）の後ろには、必ず2個改行（空白行2つ）を入れる**

  - 適用対象: すべてのドキュメントファイル（Markdown、テキストなど）

  - リストブロック全体の終了後（最後のリスト項目の後）に空行2つを入れる

  - これにより、次のセクションや見出しとの間が明確に区切られる

  - **⚠️ 重要: リスト項目の間にも空行を入れる（`7-progress-support.md`の形式を参考）**

    - オーダーリスト（`1.` `2.` `3.`）の場合、各項目の間に空行1つを入れる

    - 箇条書き（`-`）の場合も、各項目の間に空行1つを入れる

    - 例:
      ```
      1. **項目1**

      2. **項目2**

      3. **項目3**

      （ここに空行2つ）
      ```

  - **このルールは、コード以外のすべてのドキュメント・テキストファイルに例外なく適用される**

- **AI作成文章の改行ルール**

  - **⚠️ 必須: 句点（。）・疑問符（？（全角）・?（半角））の後は必ず改行する**

  - 適用対象: AIが生成する文章（アドバイス、あらすじなど）

**例:**

```
### 見出し（インデントなし）

#### サブセクション（インデントなし）

- リスト項目（インデントなし）

（ここに空行が入る）

  - ネストリスト（2スペースインデント）

（ここにも空行が入る）

次のセクション（改行2回で間に空行）
```

#### AI編集時の改行チェックリスト

**AIがドキュメントファイルに追記・編集を行う際は、完了前に必ず以下をチェックし、違反があれば即座に修正する：**

1. **見出しの前の空行チェック**

   - `## レベル2`見出しの前に空行2つあるか

   - `### レベル3以降`見出しの前に空行1つあるか

2. **見出しの後の空行チェック**

   - すべての見出し（`#`〜`######`）の直後に空行1つあるか

3. **リスト・箇条書きの前の空行チェック**

   - すべての`-` `・` `1.`で始まる行の前に空行1つあるか

   - ネストされたリストの各項目の間にも空行1つあるか

4. **リストの後の空行チェック**

   - すべてのリストブロック終了後に空行2つ（改行2回）あるか

   - オーダーリスト（`1.` `2.` `3.`）の各項目の間に空行1つあるか

   - 箇条書き（`-`）の各項目の間に空行1つあるか

5. **ピリオドで終わる文の後の空行チェック**

   - ピリオド（.）で終わる文の後ろに空行2つ（改行2回）あるか

   - `**理由:**` や `**決定事項:**` などの後ろに空行2つあるか

**⚠️ このチェックリストは、ドキュメント追記・設計書更新・README作成・すべてのAI編集において例外なく適用する。**

**編集完了前に必ず確認せよ。**

**⚠️ 特に重要: ピリオド（.）で終わる文とリストの後ろには必ず2個改行（空白行2つ）を入れること。このルールは徹底的に遵守すること。**

**⚠️ 適用範囲の明確化:**
- **このルールは、プログラミングコード以外のすべてのドキュメント・テキストファイルに適用される**
- Markdownファイル（`.md`）、テキストファイル（`.txt`）、その他のドキュメント形式すべてに適用
- コードファイル（`.ts`, `.tsx`, `.js`, `.jsx`, `.py`, `.sql` など）は除外
- 設定ファイル（`.json`, `.yaml`, `.toml` など）も除外
- **すべてのドキュメント編集時に、このルールを徹底的に遵守すること**

- **2（本書）**: **確定事項の仕様のみ**を記載する。実装で参照する決定稿。
- **7（`7-progress-support.md`）**: **未確定事項を進める中での確認事項**・検討案・相談メモ・進行中の整理を書く。確定したら仕様は2に移す。
- 未確定の案・検討中の確認事項を2に書かない。7に書く。このルールを徹底する。

### 0（`0-AI-prompt-memo.md` など）

- **ユーザーから「ここに書け」と指示がある場合を除き、AIは0に追記・リライトをしない**
- 0はユーザーが指示やメモを書くファイルのため、参照のみ可。回答・相談案・進行メモなどは0には書かず、進行中の確認用は **7** に書く

### `1-web-ai-directive-draft.md`

- このファイルの中は、AIによるリライトや書き込みを絶対にしない
- ユーザーが指示を記録しておいたり、設計構想時の草案やメモが書かれているファイルのため
- 参照のみ可能

### 進行中の確認用メモの置き場

- **進行中の確認用のメモは `7-progress-support.md` に書く**（0には書かない）

## MD版（Markdown運用）との関係・方針

本ドキュメントは「Webアプリ版（web-app）」専用の設計書。MD版（md-app）と責務を分離する。

- 実装フェーズの独立: Webは単独価値のMVPから開始、同期は後工程で段階導入。

### 同期に向けた設計スタンス（今は実装しない）

**基本方針:**

- MVP段階: Web版単独で動作、同期機能は未実装

- P5-P6段階: 手動同期ボタンで実装（自動同期・リアルタイム監視は不要）

- ユーザーが「同期」ボタンを押したタイミングでのみ同期処理を実行

**データ構造の準備（MVP段階から実装）:**

- IDと時系列: `YYMMDD`/`YYYY-MM-DD`＋UUID。競合検出可能にする。

- タイムスタンプ: `updated_at`（最終更新日時）を必ず保存

- ソース情報: `source`（`web`|`md`）を記録し、どちらで更新されたかを追跡

- スキーマ整合: WebはJSONスキーマを持ち、MD見出し構造と相互変換可能性を確保

**同期方式（P5-P6で実装）:**

- 手動同期: ユーザーが設定画面の「MD版と同期」ボタンをクリック

- 同期方向: 双方向（Web→MD、MD→Web）

- 競合解決: タイムスタンプ比較で後勝ち、または、ユーザー選択マージUI提供

- ファイル監視: 不要（手動ボタンのみ）

**メリット:**

- ✅ ユーザーが同期タイミングを完全制御

- ✅ 実装がシンプル（リアルタイム処理不要）

- ✅ ファイル監視の複雑性を回避

- ✅ 競合解決がわかりやすい

## 将来の拡張機能（P5以降で検討） --------------

### 🎭 世界観テーマ切り替え機能

**コンセプト:**

- ユーザーが複数の世界観プロファイルを設定・切り替え可能

- AIのアドバイス・あらすじの口調や比喩表現が世界観に応じて変化

- テーマ例:

  - ゴースト・オブ・ヨウテイ風（和風・蝦夷地の雰囲気）

  - ドラクエ風（勇者・魔王・冒険の世界）

  - JOJO風（スタンド・覚悟・ジョジョ節）

  - その他、ユーザーがカスタム追加可能

**実装イメージ:**

- 設定画面でテーマを選択

- プロファイル情報（世界観、口調、キャラクター設定）を保存

- AI判定APIにテーマ情報を渡してアドバイス生成

**データ構造案:**

```json
{
  "theme_id": "ghost-of-yotei",
  "protagonist_name": "辰彦",
  "world_tone": "蝦夷地の武芸者",
  "advice_style": "厳しめの師匠口調",
  "metaphor_source": "和風・自然・刀剣"
}
```

**案C: コードで2種類固定の実装手順（ユーザーは選択のみ）**

1. **定数定義**
   - `lib/ai/story-worlds.ts` などで、世界観ID（`dq` / `ghost`）ごとのプロンプト文言・システムメッセージを定数として定義する。
   - 例: ドラゴンクエスト風・ゴースト・オブ・ヨウテイ風の2種類。

2. **設定画面の変更**
   - 「物語の世界観」を自由入力テキストから、**2択（ラジオまたはセレクト）** に変更する。
   - 選択値を `localStorage`（例: `gol-story-world`）に保存。値は `dq` または `ghost`。

3. **API の変更**
   - `POST /api/ai/story` のリクエストボディに `storyWorldId`（`dq` | `ghost`）を受け取る。
   - 未指定時は既定（例: `dq`）を使う。

4. **プロンプト生成の変更**
   - `createStoryPrompt` に `storyWorldId` を渡す。
   - 世界観IDに応じて、定数からシステムメッセージ／プロンプト末尾の指示を組み立てる。

5. **日誌フォームの変更**
   - あらすじ生成時に、設定画面で保存した `storyWorldId`（localStorage から取得）を `POST /api/ai/story` に含めて送る。
```

**優先度:** P5以降で実装（MVP段階ではゴースト・オブ・ヨウテイ固定）
