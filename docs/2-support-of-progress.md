### 260406｜ヘッダー「未確定」運用メモ（注意事項）

**記載** Cursor（ユーザー依頼）

#### 一括で確定済みにしたデータ修正について

- 開発中に、Supabase の REST で `daily_logs` の `is_confirmed` を **条件付き一括更新**したことがある

- 条件が **全ユーザーの行** に当たる書き方だと、**自分以外の招待ユーザーの日誌まで確定済み**になっている可能性がある

- 本番で複数ユーザーがいる場合は、Supabase ダッシュボード等で **意図しない更新がないか** 確認しておくと安全

#### 「直近30日」の境界（JST）

- ヘッダー未確定の集計で使う `cutoffStr` は、`gol-web/lib/date-utils.ts` の `getDateStringDaysAgoJST` で **`Asia/Tokyo` の「今日」から N 日前** を YYYY-MM-DD で返している（`MAX_UNCONFIRMED_LOGS_FOR_PENDING_HEADER_SUM` が N）

- アプリの `log_date` と同じく日付は JST 基準で揃える

### 260406｜ToDo完了 → スコア確定の仕組み整理（検討中）

**記載** Cursor（ユーザー依頼）

#### いまの仕組みをざっくり説明

GOLでは「日誌」が日付ごとに1つある。日誌には「未確定」と「確定済み」の2つの状態がある。

ToDoタスクを「完了」にすると、裏で `todo_log` というレコードが作られる。この `todo_log` はどれか1つの日誌にひもづく。確定ボタンを押すと、その日誌にひもづいている `todo_log` のスコアがまとめてプロフィールに加算される。

ヘッダーの「未確定: +○G」は、まだ確定されていないスコアの合計を表示している。

#### 「todo_log はどの日誌にひもづくか？」が論点

ToDoを完了したとき、`todo_log` がどの日付の日誌に記録されるかで、スコアがどこに入るかが変わる。

#### パターン A: 現状の動き

「表示中の日誌の状態」で記録先が変わる。

- 4/5（未確定）を表示中に ToDo完了 → `todo_log` は **4/5 の日誌** に記録される

- 4/5（確定済み）を表示中に ToDo完了 → `todo_log` は **今日（4/6）の日誌** に記録される

- 今日（4/6・未確定）を表示中に ToDo完了 → `todo_log` は **今日（4/6）の日誌** に記録される

つまり、過去の未確定日誌を開いているときにToDoを完了すると、その過去日のスコアとして記録される。

この場合の問題点:

- 過去の未確定日でToDoを完了すると、ヘッダーの「未確定」（今日のデルタしか見ていない）には反映されない

- ユーザーが「あれ？ToDoを完了したのにスコアが表示されない」と混乱する可能性がある

#### パターン B: 常に今日の日誌に記録する（検討案）

どの日付を見ていても、ToDo完了 → 常に **今日の日誌** に `todo_log` を記録する。

- 4/5（未確定）を表示中に ToDo完了 → `todo_log` は **今日（4/6）の日誌** に記録

- 4/5（確定済み）を表示中に ToDo完了 → `todo_log` は **今日（4/6）の日誌** に記録

- 今日（4/6）を表示中に ToDo完了 → `todo_log` は **今日（4/6）の日誌** に記録

メリット:

- シンプル。ToDoのスコアは必ず「今日」に集まる

- ヘッダーの「未確定」は今日のデルタだけ見ればOK

- 過去の日誌にはToDoスコアが混ざらない

デメリット:

- 過去の未確定日に意図的にスコアを入れたいケースに対応できない

#### ヘッダー「未確定」表示のルール（現状の実装）

- **今日の日誌が未確定** → ヘッダーに「未確定: +○G」を表示（今日のデルタ）

- **今日の日誌が確定済み** → 「未確定」は非表示

- どの日付を見ていても、ヘッダーの未確定は **今日のデルタだけ** を表示する

- 過去の日付の日誌では未確定表示は出さない

#### 決定待ち

- パターン A（現状のまま）か パターン B（常に今日に記録）か → ユーザー判断待ち

#### パターン A のままでも「未確定スコアがある」を伝える案

Aのままだと、過去の未確定日に `todo_log` が付いたスコアは、**今日の日誌のデルタだけ**を見ているヘッダー「未確定」に乗らない。完了日以降の日誌を見ていても気づきにくい。それを補う検討案。

**案1: ヘッダーの「未確定」を全未確定日のデルタ合算にする**

- 今日の日誌だけでなく、**未確定の日誌すべて**についてデルタを計算し、合算して表示する

- 例: 4/5に+4G、今日に+2G → 「未確定: +6G」、併せて「（2日分）」などの表記も検討可

- 実装イメージ: `page.tsx` の `pendingDeltas` を、未確定 `daily_logs` を列挙して `calculateDayDeltas` を足し合わせる

**案2: バッジで「未確定の日誌が○件」とだけ知らせる**

- 金額の内訳は出さず、他にも未確定の日があることを示す。タップでその日付へ遷移するなど

**案3: 今日のダッシュボードを開いたときバナーで通知**

- 例: 「4/5の日誌が未確定です（+4G）」のようなバナー

**メモ**

- 案1はヘッダー一箇所で「合計いくら未確定か」がわかり、パターン A の柔軟性も残しやすい

- **実装（案1＋ガード）**: 未確定 `daily_logs` を `log_date` 昇順で列挙し、各日 `calculateDayDeltas` を `Promise.all` で並列実行し `sumDayDeltas` で合算（`gol-web/app/dashboard/page.tsx`）。上限は **30件（約1か月）**（`gol-web/lib/pending-header-constants.ts` の `MAX_UNCONFIRMED_LOGS_FOR_PENDING_HEADER_SUM`）。超過時はヘッダーに件数のみ表示（内訳省略）。`gol-web/lib/score-calculator.ts` に `sumDayDeltas` を追加

### 260406｜ダッシュボード｜RSC と router.refresh

**記載** Cursor

- ダッシュボードは `app/dashboard/page.tsx` で RSC として profiles・`daily_logs`・習慣・ToDo・スコア内訳などをサーバー取得している。クライアントからの Supabase/API 更新だけでは、一度サーバーが渡した props は自動更新されない。

- そのためヘッダー未確定ゴルドなどサーバー計算値を DB と揃えるには `router.refresh()` で RSC を再実行する必要があり、習慣チェック後などでも呼んでいた。

- `RouterRefreshProvider` では `refresh`（`useTransition`＋全画面スピナー）と `refreshQuiet`（`router.refresh` のみ・オーバーレイなし）を分けている。高頻度操作は `refreshQuiet`（実装: `gol-web/contexts/router-refresh-context.tsx`）。

- refresh を根本から減らすには、該当データのクライアント取得（SWR 等）への寄せや、楽観的 UI だけで足りる箇所の整理といった設計見直しが必要。

### 260401-Wed ToDoスコア設計メモ -------------

#### 260401-Wed｜確定後にToDoを完了させた場合の挙動

**記載** ClaudeCode

**方針（検討中）**: ToDoは日誌と独立した存在として扱う

- 確定後に過去の日誌を見ながらToDoを完了しても、**その日誌のスコアは変えない**
- 完了させたら「**今日（未確定）の日誌**」のtodo_logsに加算する
- 現状問題: 過去日誌を見ながら完了に動かすと `dailyLogId` が過去の日誌IDになる → 修正が必要

**現状の挙動（コード調査済み）**:

- カンバン（日誌タブ）: `isConfirmed` チェックあり → 確定後は `todo_logs` 更新なし（スコア変化なし）
- ToDoサマリータブ: `isConfirmed` チェックなし → 確定後でも `todo_logs` に書き込まれてしまう
