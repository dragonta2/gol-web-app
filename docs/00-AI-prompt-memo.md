**まとめ**

- **日誌タブ**: その日の To Do を「ドラッグでステータス変更」する画面。追加・編集・削除・サブタスクの操作はできない。
- **ToDoサマリータブ**: To Do の「一覧・追加・編集・削除・サブタスク」を扱う画面。ステータスは編集モーダルで変更できるが、ドラッグでの変更はアクティブ⇔進行中の並び替えのみ（完了へのドラッグはここにはない）。

- GitHub の Private リポはブラウザで次の手順で作成する。

**gol-web-app を Private で作る手順**

1. GitHub → New repository
2. Repository name: `gol-web-app`
3. Visibility: **Private**
4. 「Add a README file」は付けない（ローカルに既にあるため）
5. Create repository を押す
6. ローカルで、初回だけリモートを追加して push する:

   ```bash
   cd /path/to/gol/web-app
   git init
   git remote add origin https://github.com/<あなたのユーザー名>/gol-web-app.git
   git add .
   git commit -m "Initial: GOL Web版"
   git branch -M main
   git push -u origin main
   ```

   （すでに gol 配下で git 管理されている場合は、`web-app` だけを gol-web-app のルートとして押す方法になる。その場合は `git subtree split` や、`web-app` を新規 clone 先にコピーしてから init → add → push する形をとる。）

**CLI（GitHub CLI）で作る場合**

前提: [GitHub CLI](https://cli.github.com/) を入れ、`gh auth login` 済みであること。

```bash
cd /path/to/gol/web-app

# ここがまだ git 管理下でない場合だけ
git init
git add .
git commit -m "Initial: GOL Web版"

# リポ作成（Private）＋リモート追加＋push を一括
gh repo create gol-web-app --private --source=. --remote=origin --push
```

- `--private` … Private で作成
- `--source=.` … カレントディレクトリをソースとして使う
- `--remote=origin` … リモート名を `origin` に
- `--push` … 作成後に現在のブランチを push

既に gol が 1 リポで、web-app だけを別リポにしたい場合は、いったん `web-app` の中身だけを別ディレクトリにコピーし、そのディレクトリで `git init` → `add` → `commit` してから上記 `gh repo create` を実行する。

**「gol-web (modified content, untracked content)」と出た場合**

gol-web に独自の `.git` があったため、web-app からはサブモジュール扱いになっている。  
「docs と gol-web を 1 つの git で管理」するには次のように直す。

1. gol-web 内の `.git` を削除する（実施済みの場合はスキップ）
2. web-app で以下を実行:

   ```bash
   cd /path/to/gol/web-app
   git rm --cached gol-web
   git add gol-web/
   git commit -m "gol-web を通常ディレクトリに（サブモジュール解除）"
   git push origin master
   ```

   または `fix-gol-web-as-normal-dir.sh` を実行。

## 制作用メモ -------------

### 推奨順序

データ移行を先に（推奨）

理由:
テストアカウントでデータがある状態で動作確認できる
差異チェック時に実データを見ながら機能の違いを確認できる
比較的短時間で完了できる（1〜2件の手動移行で十分）

手順:
まず1〜2件を手動で移行
テストアカウントで動作確認
その後、差異チェックを実施（実データを見ながら）
差異チェックを先にする場合

メリット:
移行するデータの範囲が明確になる
移行スクリプトを改善できる可能性がある

デメリット:
時間がかかる可能性がある
データがない状態での確認になる

推奨
データ移行を先に進めることを推奨します。1〜2件を手動で移行し、テストアカウントで動作確認してから、差異チェックに進むと効率的です。
