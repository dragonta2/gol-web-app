**Q: To Do Taskの編集はどこの画面からやる？**
→ **ToDoサマリータブのみ。** 各カードの「📝編集」→ モーダルで名前・期限・報酬・難易度・タグを編集。日誌タブのカンバンには編集ボタンや編集リンクはありません。

**使いやすい導線の相談（案）**

1. **「その場で完結」を増やす**
   - 日誌のカンバンで「今日のタスクを触りたい」ときに、名前や期限を直したくなったらサマリーへタブ切り替えが必要で、文脈が切れる。
   - **案A**: 日誌のカードに「編集」リンクを追加 → クリックで **ToDoサマリータブへ切り替え＋該当タスクの編集モーダルを開く**。
     - 実装: `dashboard-tabs` で `activeTab` と「編集対象の todoId」を共有し、サマリー側で `todoId` があればモーダルを開く。
   - **案B**: 日誌のカードから **小さな編集モーダルをその場で開く**（名前・期限くらいだけ）。
     - サマリーでしかできない操作（削除・サブタスク・タグなど）は「サマリーで詳しく編集」リンクで誘導。

2. **「今日やること」の導線を短くする**
   - 今日のタスクを進めるときは **日誌タブ → カンバン** が主な入口になりやすい。
   - ここに「サマリーで追加・編集」への一目で分かるリンク（例: カンバン見出し横に「+ タスクを追加」「一覧・編集はToDoサマリー」）があると、「今日の作業」と「一覧・設定」の行き来がしやすい。

3. **役割をはっきりさせる**
   - **日誌タブ** ＝ 「その日」の実行（ステータス変更が主）。
   - **ToDoサマリー** ＝ タスクの定義・一覧・追加・編集・削除・サブタスク。
   - この分担をUI上でも示すと、「編集したいときはサマリーへ」が自然になる。
     → 日誌タブのカンバン直上などに、短い説明「タスクの名前・期限・報酬の変更は ToDoサマリー から」を出しておくのもあり。

4. **まず手を入れやすいところ**
   - **案A（サマリーへ飛んでモーダル開く）** が、実装量と分かりやすさのバランスが良い。
     - 日誌側: カードに「📝 編集」などのリンクを追加。
     - クリックで `setActiveTab('todo-summary')` かつ「この todoId で編集モーダルを開く」情報を渡す。
     - サマリー側: URL クエリや Context で `?editTodo=xxx` 相当を受け取り、マウント時にそのタスクの編集モーダルを開く。

**実装するなら、まずは案A（日誌のカードから「編集」→ ToDoサマリータブへ切り替え＋該当タスクの編集モーダルを開く）から着手するのがおすすめ。**


## 260127-火 -------------

### To Do 操作の動線（現状の整理）

**どの操作がどの画面からできるかの一覧**

- **新規タスク追加** … ToDoサマリーのみ。「+ 新規タスク」→ モーダルで名前・期限・報酬・タグなど入力。日誌タブのカンバンには追加ボタンなし。

- **ステータス変更**（アクティブ⇔進行中⇔完了） … 日誌タブのカンバン。ドラッグでカラム間移動。進行中カードの「← アクティブに戻す」でアクティブに戻せる。完了→アクティブ/進行中もドラッグで可能。

- **ステータス変更**（編集経由） … ToDoサマリー。各カードの「編集」→ モーダル内のステータスを変更して保存。ドラッグより細かい変更用。

- **タスクの編集**（名前・期限・報酬・難易度・タグ） … ToDoサマリーのみ。各カードの「📝編集」→ モーダルで編集。日誌のカンバンからは編集できない。

- **タスクの削除** … ToDoサマリーのみ。各カードの「🗑削除」。日誌のカンバンからは削除できない。

- **サブタスクの追加・編集・完了・削除** … ToDoサマリーのみ。各カードで「▶ サブタスク」を展開 → 「+ 追加」／各サブタスクの編集・削除・チェック。日誌のカンバンではサブタスクは触れない。

**まとめ**

- **日誌タブ**: その日の To Do を「ドラッグでステータス変更」する画面。追加・編集・削除・サブタスクの操作はできない。
- **ToDoサマリータブ**: To Do の「一覧・追加・編集・削除・サブタスク」を扱う画面。ステータスは編集モーダルで変更できるが、ドラッグでの変更はアクティブ⇔進行中の並び替えのみ（完了へのドラッグはここにはない）。

**動線整理の検討候補**

- 日誌のカンバンから「編集」リンクを出して ToDoサマリー（該当タスクの編集モーダル）へ飛ばす
- ToDoサマリーからカンバン的なビューを開く／日誌タブへ誘導する

### マークダウン版とのデータの整合性についての相談（一旦保留）

**ステータス: 検討中**

#### 背景・目的

**なぜデータ連動させたいのか:**

- これまで日記として書き続けてきたマークダウン版を放置したくない

- 長年蓄積してきたデータを活用したい


**現状の課題:**

- **マークダウン版の課題**:

  - 書くこと自体が時間がかかる

  - **特にAIの処理が遅くて時間がかかってしまう**（主要な課題）

- **Web版への期待**:

  - AI処理の高速化

  - もっと手早く書ける方法があるのではないか


**検討事項:**

- 実際に運用してみないとわからないが、Web版とマークダウン版、どちらがいいのだろうか

- 両方のデータを連動させることで、比較検討しやすくしたい


#### 整合性に関する主な課題

**1. データ構造の違い**

- **MD版**: ファイルベース（1つのMarkdownファイルに1ヶ月分の日誌を集約）

- **Web版**: データベース（日付ごとに`daily_logs`テーブルに保存）

- **課題**: 同期時にデータ構造をどう対応付けるか


**2. 習慣データの整合性**

- **MD版**: 習慣名は自由記述（例: "GOLリストを記述｜ログインボーナス｜1日に一回のみ"）

- **Web版**: `habits.habit_name`は登録済みの習慣のみ

- **課題**: 習慣名のマッチング精度、マッチしない場合の対応


**3. 数値入力習慣の整合性**

- **MD版**: 習慣名に数値が含まれる（例: "懸垂｜10回"）

- **Web版**: `input_type = 'number'`の場合、`habit_logs.count`に数値を保存

- **課題**: 数値の抽出方法、複数選択肢がある場合の処理


**4. EXP配分の整合性**

- **MD版**: 完了済みToDoに`身体: +0 / 頭脳: +1 / 精神: +1`形式で記載

- **Web版**: `todo_logs.exp_body_earned`, `exp_mind_earned`, `exp_spirit_earned`に保存

- **課題**: EXP配分の同期タイミング、累積値の扱い


**5. ポイント・EXPの累積値の整合性**

- **MD版**: AI判定結果に累積値が記載（例: "身体: +4｜現在の累積 481"）

- **Web版**: `profiles`テーブルで累積値を管理

- **課題**: 同期時に累積値をどう扱うか（MD版の累積値は参考情報のみ？）


**6. 日付フォーマットの違い**

- **MD版**: `YYMMDD-W`形式（例: `251120-木`）

- **Web版**: `YYYY-MM-DD`形式（例: `2025-11-20`）

- **課題**: 日付フォーマット変換の精度（年の推測方法）


**7. データの欠損・不一致**

- **MD版にのみ存在するデータ**: なし（主要データは両方に存在）

- **Web版にのみ存在するデータ**: なし（主要データは両方に存在）

- **課題**: 同期時にデータが欠損した場合の対応


#### 整合性を保つための方針（検討事項）

**方針1: 完全同期（双方向）**

- MD版とWeb版のデータを完全に同期

- 競合解決が必要

- 実装が複雑


**方針2: 一方向同期（MD → Web または Web → MD）**

- 一方をマスターとして、もう一方に反映

- 競合解決が不要

- 実装が比較的簡単


**方針3: 選択的同期**

- 特定のデータのみ同期（例: 日誌本文、一言感想のみ）

- 整合性の課題が少ないデータから優先的に同期

- 段階的な実装が可能


#### 統一方針の決定 ✅ **確定（更新）**

**決定事項（260120-火）:**

- **方針: Web版のデータを新しいレポートファイルとしてMarkdown形式で出力する**

- **理由: 完全同期機能の実装はコストがかかりそうなので、一旦この方針で進める**

- **重要な方針変更:**

  - **既存のMD版はそのまま置いておく**（変更しない）

  - **別の場所に新しいレポートファイルとしてMarkdownファイルを出力する**

  - 既存のMD版のファイルを上書きするのではなく、新しい場所にレポートを生成する

  - 一方向同期のみ（Web → 新レポート）、MD → Web同期は不要

  - 実装が大幅に簡素化される


**基本方針:**

- **ベースは既存MD版のデータ構造に合わせて、レポート出力形式を作る**

- Web版で追加された良い機能もレポートに反映するか、あるいはWeb版にあってMD版にない機能は、レポートに追記する場合は空欄にするか

#### 相談したいこと（上から順に検討）

**基本方針に関する相談:**

**1. Web版の追加機能の扱い**: Web版にあってMD版にない機能は、どう扱うか？

**検討事項:**

- MD版に追記する場合、空欄にするか？

- ◯｜MD版に追記する場合、デフォルト値を設定するか？

- MD版には無視して、Web版でのみ管理するか？


**🤖 AI推奨案:**

- **方針: Web版でのみ管理し、MD版には反映しない（推奨）**

- **理由:**

  1. **MD版の構造をシンプルに保つ**: MD版は人間が読み書きする形式なので、複雑なメタデータを追加すると可読性が下がる

  2. **ベースはMD版の構造に合わせる方針**: MD版に存在しない機能は、MD版には含めない方が一貫性がある

  3. **Web版の追加機能はWeb版の利点**: `exclude_weekends`、`display_order`などはWeb版のUI機能として活用し、同期時には無視する

- **具体的な対応:**

  - `exclude_weekends`, `exclude_from_complete`, `display_order`, `is_custom`: **Web版でのみ管理、MD版には反映しない**

  - `base_consumption`: **固定値として扱い、MD版には記載しない**（MD版では計算で導出可能）

  - `ai_condition_body`, `ai_condition_mood`: **廃止予定なので無視**

  - `status`（'in_progress'）: **MD版では「アクティブ」として扱う**（MD版には「アクティブ」「完了済み」のみ）

- **例外:**

  - 将来的にMD版でも必要になった機能は、その時点でMD版の構造に追加を検討


---

**2. 同期の方針**: どの方針で進めるべきか？

**検討事項:**

- 背景を踏まえると、**Web版を主に使いつつ、MD版のデータも活用できる**形が良さそう

- 一方向同期（Web → MD）で、Web版で書いた内容をMD版にも反映させる形はどうか？

- または、選択的同期で、まずは日誌本文・一言感想など簡単なデータから同期する形はどうか？

- **重要**: 運用が始まっていないので、どちらが使いやすいかわからない。使い勝手の良い方を主流で使っていくので、もしMDの方が使いやすかったら、MD→Webも必要

- **新たな方針検討**: もしWeb版が主流となって使うようになるのであれば、MD版というのはWeb版のただのレポートでもいいのではないか？

  - MD版側で書くわけじゃなくて、あくまでもWeb版のテキストレポート

  - これだったら難易度はグッと下がる？


**🤖 AI推奨案（更新）:**


**MD → Webの難易度分析:**

- **技術的難易度: 中〜高**

  - **課題1: マークダウンパーサーの実装**

    - MD版の構造が複雑（「処理済み/最新話」と「処理前/ドラフト/当日日誌」の2つのセクション）

    - 正規表現パターンの精度が重要（データ抽出の失敗リスク）

    - 実装済みの`migrate-md-to-web.ts`スクリプトで課題を確認済み

  - **課題2: 習慣名のマッチング**

    - MD版は自由記述、Web版は登録済み習慣のみ

    - マッチしない場合の処理が必要

  - **課題3: 数値入力習慣の抽出**

    - 習慣名から数値を抽出する処理が必要

    - 複数選択肢がある場合の判定が複雑

  - **課題4: ファイルアクセス**

    - GitHub API経由でのファイル読み込みが必要（実装コストあり）

- **実装コスト: 高**

  - パーサーの実装・テストに時間がかかる

  - エラーハンドリングが複雑

  - データ抽出の精度を上げるのに時間がかかる
