## 自動日付追記（launchd） --------------

`docs/0-AI-prompt-memo.md` に、Mac 起動・スリープ解除のタイミングで当日の作業欄を自動追記する仕組み。

### 概要

- Mac を開いたとき（ログイン時・スリープ解除後）に即時実行
- 以降 1 時間ごとにバックグラウンドでチェック
- 当日の見出しがすでにある場合はスキップ（二重書き込みなし）
- 月が変わったとき、月見出しがなければ自動で作成

### 挿入される内容

```
## YYMMDD-曜 -------------

さあ、続きからはじめよう！！
今日の日付は YYMMDD-曜

前回までの作業は進捗用の3番メモを参照して

今日もよろしくお願いします！！

```

月見出し `## YYMM- -------------` の直下に挿入される。

### 構成ファイル

- **スクリプト**: `/Users/ta2/ALL-DTA2/.automation/scripts/add-daily-prompt.sh`
- **launchd plist**: `~/Library/LaunchAgents/com.ta2.daily-prompt.plist`
- **ログ**: `~/Library/Logs/daily-prompt.log` / `daily-prompt.error.log`

### 詳細ドキュメント

スクリプトの詳細、注意事項、トラブルシューティングは以下を参照してください：

```
/Users/ta2/ALL-DTA2/.automation/README.md
```

### launchd の登録・解除コマンド

```bash

# 登録（初回のみ）
launchctl load ~/Library/LaunchAgents/com.ta2.daily-prompt.plist

# 解除（停止したいとき）
launchctl unload ~/Library/LaunchAgents/com.ta2.daily-prompt.plist

# 手動で今すぐ実行
launchctl start com.ta2.daily-prompt
```

### 注意事項

- `0-AI-prompt-memo.md` の月見出し（`## YYMM- -------------`）が存在しない場合、スクリプトがファイル先頭付近に月見出しごと自動作成する
- Mac がログイン状態であれば動作する（スリープ有無は問わない）

### 習慣チェックの保存タイミング（メモ）

習慣のチェック状態は「日誌を保存」とは別で、**チェック操作のたびに即時DB（`habit_logs`）に保存**される。そのため、習慣だけつけて日誌本文を保存せずにカレンダーで別の日付に遷移しても、元の日付に戻ればチェックは残っている。日誌の保存は日誌テキスト・感想・確定状態用であり、習慣ログの保存とは独立している。

### Supabase Auth メール変更フロー（メモ）

設定画面からアカウント（メールアドレス）を変更する場合の Supabase 側の流れを整理。実装時参照用。

- **API:** クライアントで `supabase.auth.updateUser({ email: 新しいメール })` を呼ぶ

- **確認フロー（Secure Email Change 有効時）**
  - 新メールに「変更確認」用のトークン（または確認リンク）が送られる
  - 旧メールにも「確認」用のリンクが送られる（通知だけではない）
  - **両方のメールで確認リンクを開かないとメールは更新されない**（新メールだけ開いても変わらない）
  - ダッシュボード: Authentication > Email Templates で「Change email address」「Email address changed notification」をカスタム可能

- **トラブルシュート: 確認メールを開いたのにメールが変わらない**
  - **Secure Email Change が有効**になっている可能性が高い。Supabase Dashboard → **Authentication** → **Providers** → **Email** を開く
  - **Secure email change** が ON の場合 → **旧メールに届いたリンクも開く**（新メール・旧メールの両方で確認が必要）
  - 新メールだけで完了させたい場合は **Secure email change を OFF** にする（その場合、新メールの確認リンクを開くだけで変更完了）

- **実装時のポイント**
  - メールが届いただけでは変更されない。届いたメール内のリンクを開いて初めて変更が完了する旨を案内する
  - 変更依頼後、「新メールに送った確認リンクを開いてください」と案内する画面を用意する
  - 確認完了まで「未確認」状態の扱い（ログイン制限など）を設計で決める
  - `profiles` などでメールを表示している場合は、Auth の `user.email` を正とする（Auth 更新後に同期）

- **リダイレクト・端末の注意**
  - 確認リンクを開いたあと、Supabase が **URL Configuration** の Site URL / Redirect URLs に設定したURLへリダイレクトする。この設定が必要
  - 確認リンクは**リダイレクト先に、開く端末からアクセスできる必要がある**。ローカル（localhost）の場合は**同一PCで**リンクを開く必要がある。スマートフォンでは localhost に届かないため「ページを開けません」になる。本番では Site URL / Redirect URLs に本番URLを設定すればスマホからも問題なく完了できる

- **参考:** [Supabase Auth - updateUser](https://supabase.com/docs/reference/javascript/auth-updateuser)、Email Templates（Change email address）

## ドキュメント書式統一ルール --------------​

**適用範囲:** プログラミングコード以外のすべてのドキュメントファイル

- **Markdownファイル**（`.md`）: README.md、設計書、進捗表、開発ログ、メモ類など
- **テキストファイル**（`.txt`）: すべてのテキストファイル
- **その他のドキュメント形式**: すべてのドキュメントファイル

**⚠️ 除外対象:**
- プログラミングコード（`.ts`, `.tsx`, `.js`, `.jsx`, `.py`, `.sql` など）
- 設定ファイル（`.json`, `.yaml`, `.toml` など）
- その他のコードファイル

**⚠️ 重要: このルールは、コード以外のすべてのドキュメント・テキストファイルに例外なく適用される。**

#### 日付の並び順ルール

- **すべての日付を伴う記録は降順（新しい日付が上）**

- 最新の情報が常にファイルの上部に来るようにする

- 適用対象:
  - 進捗表（`3-project-progress.md`）
  - 開発ログ（`4-dev-log.md`）
  - メモ類（`2-support-of-progress.md`など）
  - その他、日付見出しを持つすべてのファイル

- 新しい日付の追記は、既存の日付の上に挿入

- **メモ類への追記ルール:**
  - AIがメモ類（`2-support-of-progress.md`など）に追記する場合は、原則降順（後入れ先追加）で記載する
  - 新しい日付のセクション（`## YYMMDD-曜日`）を一番上に作成し、その中に新しい内容を記載する
  - 既存の日付セクションは新しい日付セクションの下に配置する

#### インデントルール

- **見出し（すべてのレベル）はインデントなし**

  - 折りたたみ機能を正常に動作させるため

- リストの第1レベルはインデントなし

- ネストされたリスト（第2レベル以降）のみインデントを付与（2スペース）

#### 表記ルール（Table・リスト）

- **特別な指示がない限り、Table（表）表記は使わず、リストで書く**

- **リストの各項目の間には改行を1つ入れる**

#### 改行ルール

- **見出しの前の改行ルール**

  - `## レベル2`の見出しの前には、3つの改行（空行2つ含む）

  - `### レベル3以降`の見出しの前には、2つの改行（空行1つ含む）

- **リストや箇条書きの前の改行ルール**

  - `-` で始まるリスト行の前には、2つの改行（空行1つ含む）

  - `・` で始まる箇条書き行の前には、2つの改行（空行1つ含む）

  - `1.` `2.` `3.` などのオーダーリスト行の前には、2つの改行（空行1つ含む）

- **すべてのリストブロックの後ろにつねに改行を入れる**

  - 人間の読みやすさを重視するため

  - 第1レベルのリスト、ネストされたリスト（第2レベル以降）ともに、リスト項目の終了後に空行を2行追加（改行2回で、間に空行が入る）

  - ネストされたリストにも適用される（読みやすさのため）

- **ピリオド（.）で終わる文の後ろの改行ルール**

  - **⚠️ 必須: ピリオド（.）で終わる文の後ろには、必ず2個改行（空白行2つ）を入れる**

  - 適用対象: すべてのドキュメントファイル（Markdown、テキストなど）

  - 例: `**理由:**` の後ろ、`**決定事項:**` の後ろなど、ピリオドで終わる文の直後に空行2つを入れる

  - これにより、次のセクションやリストとの間が明確に区切られる

  - **このルールは、コード以外のすべてのドキュメント・テキストファイルに例外なく適用される**

- **リスト（オーダーリスト、箇条書き）の後ろの改行ルール**

  - **⚠️ 必須: すべてのリスト（`1.` `2.` `3.` などのオーダーリスト、`-` で始まる箇条書き）の後ろには、必ず2個改行（空白行2つ）を入れる**

  - 適用対象: すべてのドキュメントファイル（Markdown、テキストなど）

  - リストブロック全体の終了後（最後のリスト項目の後）に空行2つを入れる

  - これにより、次のセクションや見出しとの間が明確に区切られる

  - **⚠️ 重要: リスト項目の間にも空行を入れる（`2-support-of-progress.md`の形式を参考）**

    - オーダーリスト（`1.` `2.` `3.`）の場合、各項目の間に空行1つを入れる

    - 箇条書き（`-`）の場合も、各項目の間に空行1つを入れる

    - 例:
      ```
      1. **項目1**

      2. **項目2**

      3. **項目3**

      （ここに空行2つ）
      ```

  - **このルールは、コード以外のすべてのドキュメント・テキストファイルに例外なく適用される**

- **AI作成文章の改行ルール**

  - **⚠️ 必須: 句点（。）・疑問符（？（全角）・?（半角））の後は必ず改行する**

  - 適用対象: AIが生成する文章（アドバイス、あらすじなど）

**例:**

```
### 見出し（インデントなし）

#### サブセクション（インデントなし）

- リスト項目（インデントなし）

（ここに空行が入る）

  - ネストリスト（2スペースインデント）

（ここにも空行が入る）

次のセクション（改行2回で間に空行）
```

#### AI編集時の改行チェックリスト

**AIがドキュメントファイルに追記・編集を行う際は、完了前に必ず以下をチェックし、違反があれば即座に修正する：**

1. **見出しの前の空行チェック**

   - `## レベル2`見出しの前に空行2つあるか

   - `### レベル3以降`見出しの前に空行1つあるか

2. **見出しの後の空行チェック**

   - すべての見出し（`#`〜`######`）の直後に空行1つあるか

3. **リスト・箇条書きの前の空行チェック**

   - すべての`-` `・` `1.`で始まる行の前に空行1つあるか

   - ネストされたリストの各項目の間にも空行1つあるか

4. **リストの後の空行チェック**

   - すべてのリストブロック終了後に空行2つ（改行2回）あるか

   - オーダーリスト（`1.` `2.` `3.`）の各項目の間に空行1つあるか

   - 箇条書き（`-`）の各項目の間に空行1つあるか

5. **ピリオドで終わる文の後の空行チェック**

   - ピリオド（.）で終わる文の後ろに空行2つ（改行2回）あるか

   - `**理由:**` や `**決定事項:**` などの後ろに空行2つあるか

**⚠️ このチェックリストは、ドキュメント追記・設計書更新・README作成・すべてのAI編集において例外なく適用する。**

**編集完了前に必ず確認せよ。**

**⚠️ 特に重要: ピリオド（.）で終わる文とリストの後ろには必ず2個改行（空白行2つ）を入れること。このルールは徹底的に遵守すること。**

**⚠️ 適用範囲の明確化:**
- **このルールは、プログラミングコード以外のすべてのドキュメント・テキストファイルに適用される**
- Markdownファイル（`.md`）、テキストファイル（`.txt`）、その他のドキュメント形式すべてに適用
- コードファイル（`.ts`, `.tsx`, `.js`, `.jsx`, `.py`, `.sql` など）は除外
- 設定ファイル（`.json`, `.yaml`, `.toml` など）も除外
- **すべてのドキュメント編集時に、このルールを徹底的に遵守すること**

## 体調・気分スコアのロジック（AI判定） --------------

日誌の「AI判定を実行」により、**体調スコア（condition_body）** と **気分スコア（condition_mood）** が0〜100の整数で付与される。このスコアは獲得ゴルド・EXPの計算の基準になる。

### いつ・誰が決めるか

- **トリガー**: ユーザーが日誌画面で「AI判定を実行」を押したとき（一括生成API `POST /api/ai/batch` が呼ばれる）

- **判定者**: GPT-4o mini（システム指示で「厳格なコーチ」役）。日誌本文と一言感想だけを入力として受け取り、JSONで体調・気分スコアと判定理由（reasoning）を返す

- **保存先**: その日の `daily_logs` の `ai_condition_body` / `ai_condition_mood` / `ai_reasoning`。確定ボタンで profiles に反映されるまで、スコアは日誌レコード上だけの値

### スコアに影響する入力（何を元に判定するか）

- **主な入力**: **日誌本文** と **一言感想**

- **参考として渡す入力**: その日に**実行した習慣**の名前一覧と、**完了したToDo**の名前一覧。判定プロンプトに「【実行した習慣】」「【完了したToDo】」として含め、体調・気分の判定の参考にするとともに、reasoning（判定理由）に習慣・ToDoの達成に触れてもよい旨を指示している（実装: `createJudgmentPrompt` の第4・第5引数、batch API で habit_logs / todo_logs から取得）

- プロンプトでは「日誌と一言感想を読んで、体調スコアと気分スコアを0-100点で判定してください」と指示しており、**採点基準の細かい項目（例: 睡眠何時間で何点）は定義していない**。AIが文脈と習慣・ToDoの達成状況から解釈する

### スコアの解釈（AIに任せている部分）

- **体調スコア（condition_body）**: 身体的な調子。例として、睡眠・疲れ・体の不調・運動・食事などが含まれうるが、項目の列挙はプロンプトには書いていない

- **気分スコア（condition_mood）**: 精神・感情の状態。例として、テンション・ストレス・やる気・不安・喜びなどが含まれうるが、同上

- どちらも **0〜100の整数**。未入力やパース失敗時は50として扱う（実装: `app/api/ai/batch/route.ts`）

### 獲得ゴルド・EXPへの換算

- 体調・気分が決まったあと、**サーバー側の計算式**で1日あたりの獲得ゴルドとEXPを算出する（AIはゴルド・EXPの数値は出さない）

- **ゴルド**: （体調＋気分）/2 の平均を定数で割った値（四捨五入）。**上限目安: 1日あたり最大8**。実装: `AI_POINTS_DIVISOR`（大きいほど付与は少ない）

- **身体EXP**: 体調スコアを定数で割った値。**頭脳EXP**: 上記平均を定数で割った値。**精神EXP**: 気分スコアを定数で割った値。**各EXPの上限目安: 1日あたり最大4**。実装: `AI_EXP_DIVISOR`

- 上記定数は `gol-web/app/api/ai/batch/route.ts` の `calculatePointsAndExp` と先頭の定数で変更可能

### 運用イメージ（どこに何を置くか）

- **フロント＋API（Next.js）**: Vercel などにデプロイ。ユーザーがアクセスする URL をここに張る

### 環境変数一覧

本番（Vercel）・ローカル（`.env.local`）で使用する環境変数の一覧。**秘密情報（キー・パスワード・具体的なメールアドレス）はこのファイルには書かず、別管理とする。**

**必須（Supabase）**

- **NEXT_PUBLIC_SUPABASE_URL**: 接続先 Supabase プロジェクトの URL。取得元: Supabase ダッシュボード → 対象プロジェクト → Project Settings → API の「Project URL」

- **NEXT_PUBLIC_SUPABASE_ANON_KEY**: 匿名（anon）キー。ブラウザから読まれるため「公開してもよい」キー。取得元: 上記同じ画面の「Project API keys」の anon / public キー（service_role とは別）

**必須（AI 機能を使う場合）**

- **OPENAI_API_KEY**: OpenAI API 呼び出し用の秘密キー。サーバー側のみ使用。取得元: https://platform.openai.com/ → API keys で発行

**任意（管理者・テスト用）**

- **NEXT_PUBLIC_ADMIN_EMAILS**: 管理者として扱うログインメールアドレス（カンマ区切り）。このメールでログインしたユーザーに「管理者用の設定」が表示され、`/settings/admin` にアクセス可能。取得元: なし（運用で決めたメールを列挙）

- **NEXT_PUBLIC_TEST_EMAILS**: テスト用アカウントのメールアドレス（カンマ区切り）。ここに含まれるメールでログインしたユーザーは管理者と同様に、レベル閾値の編集と「管理者用の設定」の表示・`/settings/admin` へのアクセスが可能。取得元: なし（運用で決めたメールを列挙）

**任意（Notion から日誌を取り込む機能を使う場合）**

- **NOTION_API_KEY**: Notion API 用シークレット。取得元: Notion → 設定 → コネクション → 新規インテグレーション（内部）のシークレット

- **NOTION_JOURNAL_DB_ID**: 取り込み元となる Notion データベースの ID。取得元: Notion で対象 DB を開いたときのブラウザ URL の「?」より前のパス末尾（32文字の英数字）

### 利用方針・ホスティング選定（少人数運用）

**自分も本番 URL で利用する**

- 当面は自分＋友達 1 名など少人数で利用する想定

- **開発者（自分）も、普段の利用は Vercel にデプロイした本番 URL を使う**のがおすすめ

- 理由: 友達と同じ環境にすることで本番でしか起きない不具合に気づきやすい。Google ログインのリダイレクトも本番 URL で試せる。データは Supabase 本番 1 本にまとまる

- 開発・デバッグ時だけ localhost を使い、試し終わったら push して本番で確認する運用にする

**ホスティングは Vercel でよいか / Amplify とのコスト比較**

- **2 名程度なら Vercel も AWS Amplify もコスト差はほぼない**（どちらも無料枠で収まりやすい）

- **GOL では Vercel を推奨**
  - Next.js の開発元のサービスで相性が良い。デプロイは GitHub 連携で push するだけ
  - 認証・DB は Supabase を使うため、Amplify の Cognito や DynamoDB は使わない。比較しているのは「Next.js をどこにホスティングするか」だけ
  - この構成・規模では Amplify のコスト的メリットはほぼなく、設定の手軽さで Vercel の方が有利

### 料金がかかるもの（目安）

**Vercel（Next.js のホスティング）**

- 無料枠: 個人利用の Hobby プランで小規模なら 0 円で運用可能

- 有料: Pro などでチーム・商用利用時。従量やビルド時間で変動。公式の料金ページを参照

**Supabase（認証・DB）**

- 無料枠: 一定の DB サイズ・API リクエスト数まで 0 円

- 有料: 超過分や Pro プラン。ユーザー数・保存データ量が増えると検討

**OpenAI API（GPT-4o mini 等）**

- 従量課金: リクエストあたりのトークン数で課金。AI 判定・アドバイス・あらすじの利用量に応じて変動

- 無料枠: 新規アカウントのクレジットなどは公式案内を参照。運用が長くなればほぼ 100% 従量

**まとめ**

- 個人・少人数利用なら「Vercel 無料 + Supabase 無料 + OpenAI の従量」で月数百円〜数千円程度になる想定

- ユーザー数・AI 利用回数が増えると Supabase と OpenAI の費用が主に増える

### 運用スケジュール（いつ何をするか）

**初回セットアップ（1 回だけ）**

- Vercel にリポジトリを連携し、本番用プロジェクトを作成

- Supabase で本番用プロジェクトを作成。必要な SQL（テーブル・RLS・トリガーなど）を SQL Editor で実行

- 環境変数の設定: 上記「環境変数一覧」を参照し、必要な項目を Vercel に設定する

- Supabase の認証設定: 本番 URL を Redirect URLs に追加。Google OAuth を使う場合はクライアント ID / シークレットを設定

- 新規ユーザー初期値を使う場合: `set-new-user-defaults.sql` を本番 Supabase で 1 回実行。お知らせを使う場合: `create-announcements-table.sql` を 1 回実行

**定期・継続作業**

- **デプロイ**: 通常は `main` への push で Vercel が自動ビルド・デプロイ。手動でデプロイする場合は Vercel のダッシュボードや CLI から実行

- **DB の変更**: スキーマ変更や新しい SQL スニペットがあるときだけ、Supabase SQL Editor で必要な SQL を実行。実行内容はドキュメント（例: `docs/sql-snippet/`）に残す

- **監視**: 落ちていないか・エラーが増えていないかは、Vercel の Functions ログ・Supabase の Logs を必要に応じて確認

**障害・不具合が出たとき**

- まず Vercel のデプロイ状態・ビルドログ、Supabase のサービスステータスを確認

- 認証まわり: Supabase の Redirect URLs・環境変数・Cookie 設定を再確認

- DB まわり: RLS ポリシーやトリガーが本番で正しく入っているか、必要なら SQL を再実行または修正して反映

**バックアップ・復旧**

- Supabase はプロジェクト単位のバックアップ・PITR が有料プランで利用可能。無料枠の範囲では手動エクスポートなどで必要に応じて対応

- 重要な変更前には、スキーマやポリシーを SQL ファイルとして `docs/sql-snippet/` などに残し、同じ手順で再実行できるようにしておく
